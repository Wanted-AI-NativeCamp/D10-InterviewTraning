## 1. 현재 프로토타입 (코드 분석 기준)

-   Streamlit 단일 앱: `app.py`(화면) · `coach.py`(계산 · 리포트) · `llm.py`(OpenAI 호출 한 곳) · `prompts.py`(프롬프트 · 스키마) · `data/questions.csv`(질문 은행 103문항, ID 칸 없음).

-   저장: Markdown v1 리포트 (`interview-data` 숨은 주석 · `version: 1`), **파일 1개 = 회차 1개**. 평가 후에만 저장 가능. 서비스 내부 저장 없음.
-   회차 번호: 이어하는 리포트 1개의 회차 + 1.

## 4. 기존 Markdown v1 기록 처리

P0-01 에서 현재 코드로 만든 샘플(`d10-interview/tests/fixtures/v1/`)로 확인한 결과다.

| 분류 | 형식 | 현재 동작 |
|---|---|---|
| 정상 복원 | `version: 1`, 직군이 질문 은행에 있음, 평가 데이터(`session`) 포함, 질문 5개가 질문 은행과 같은 글자 | 평가 · 재도전 · 실마리 · 사전 탐색 · 연습 대본까지 복원 |
| 부분 복원 | 평가 데이터 저장 기능 전 옛 리포트 / 평가 없는 기록 / 면접관이 없는 직군 | 파일은 읽히지만 '면접 없이 이어 하기' 불가 (점수 · 질문만) 또는 앱이 막음 |
| 거부 | 숨은 데이터 없음 · 깨진 JSON · 잘린 JSON · `version` 이 1 이 아님 · 모르는 직군 · 지원 정보 칸 형식 오류 | 한국어 한 줄 오류 |

v1 → 1차 구조 변환 원칙:

-   v1 파일은 계속 읽는다. 새 v2 형식이 v1 파서와 호환된다고 가정하지 않는다 (v2 는 `version: 2` 로 구분).
-   v1 회차 하나를 회차 레코드 하나로 변환한다. 같은 v1 기록을 반복해 불러와도 같은 `round_id` 로 식별되게 한다 (매핑 방식은 미확정).
-   질문은 질문 은행에서 `question_id` 를 찾아 연결한다.
-   현재 질문 은행에 없는 과거 질문 (확정): 당시 질문 원문 · 최초 제출 답변 · 기존 평가 결과 · 재도전 답변과 평가 이력 · 기록의 연결 관계를 보존하고, 그 질문에도 기존 원문으로 재도전할 수 있다. 과거 평가는 수정하거나 다시 계산하지 않으며, 다른 질문에 임의로 연결하지 않는다.
-   질문 ID 매핑에 실패했을 때의 구체적인 처리 방식(내부 식별 · ID 생성 · 변환 · 저장)은 **미확정**이며 P1 에서 결정한다.
-   v1 재도전 기록은 재도전 기록(`attempt_id`)으로 옮긴다. v1 의 재도전 횟수 칸(`retry_counts`)은 제한용 카운터라 v2 에 저장하지 않는다.
-   구형 파일은 사용자 컴퓨터의 원본을 그대로 두며 자동으로 덮어쓰지 않는다.

## 5. 회귀 테스트

-   자동: `d10-interview` 폴더에서 `python -m unittest discover tests` (P0 기준 80개). 빠른 테스트: `-p "test_[!a]*.py"`.
-   수동: `d10-interview/tests/manual_checklist.md` (59개 항목, 실제 브라우저 · 실제 AI 점검은 미실시).
-   v1 기준 샘플과 기준값(`tests/fixtures/v1/`)은 변경 전 코드 기준이므로 다시 만들지 않는다.
-   목표 정책으로 바뀌는 동작(예: 재도전 3회 제한, 빠른 피드백 면접관)의 기존 테스트 · 점검 항목은 해당 작업에서 의도적으로 갱신한다.

## 8. 2차 MVP 전환 (v2.1 계획의 M1~M6 을 2차로 이관)

### 8.0 v2.1 변경 매핑 원안 (2차 관련 항목 보존)

v2.1 판의 매핑 중 2차 범위 항목이다. 1차 범위 항목은 2장으로 옮겼다.

| 기존 | 신규 (v2.1 원안) | 조치 | v2.3 분류 |
|---|---|---|---|
| 면접 시작 | 회사/직무 선택 후 면접 | 유지·확장 | 1차: 회사 선택은 선택 항목, 미지정은 '기타' (2장). 취업 관리 회사 참조는 2차 |
| 경험 일괄 입력 | 프로젝트별 독립 경험 카드 | 분리 | 2차 (M1) |
| 재도전 | 답변 이력·퀘스트 연동 | 확장 | 답변 이력은 1차, 퀘스트 연동은 2차 |
| 리포트 | 경험/답변별 평가 및 비교 | 확장 | 답변별 평가 · 비교는 1차 기존 기능, 경험별 평가는 2차 |
| 면접 후 Markdown 저장 | 경험만 / 경험+면접 / 면접만 내보내기 | 핵심 수정 | 1차: 전체 기록 v2 통합 저장. 범위별 내보내기는 2차 요구사항 후보 (선택 저장 UX 미확정) |
| Markdown 이어하기 | 세션 내부 저장/이어하기 + 구형 파일 호환 | 전환 | 1차: Markdown 이어하기 유지 · v1 호환. 내부 저장은 2차 저장 방식 검토 대상 (미확정) |
| 위원 4명 평가 | 고정 루브릭 평가 | 팀 결정 후 전환 | 결정됨: 위원 4명 체계 유지 |

### M1. 데이터 분리

Project, ExperienceCard, ExperienceVersion, InterviewAnswer, Evaluation,
Quest 엔터티를 독립화. 기존 경험 입력은 임시 카드로 전환할 수 있도록
설계. (1차의 회차 레코드 · 질문 ID · 메시지 확장 정보와 연결)

### M2. 경험 관리 및 독립 내보내기

프로젝트·카드 CRUD, 경험만 Markdown 다운로드. **면접 기록이 없어도
동작하는지 우선 QA**.

### M3. 면접 UI 연동

질문별 추천/2개 비교, 참고 여부, 답변 draft 유지, 제출 시 버전 고정. 면접 중 경험 카드는 조회 · 비교 · 선택 · 참고만 한다 (v2.1 의 '사이드 패널 수정'은 PRD 와 충돌해 삭제).

### M4. 평가·퀘스트

경험 강화/전달 강화 매핑, 과거 평가 불변성 검증. (AI 평가 결과 저장은 1차에서 한다.)

### 8.2 v2.1 의 구형 Markdown 처리 원칙 (보존)

-   구형 파일 샘플과 현재 파서 확인 전까지 자동 마이그레이션을 보장하지 않는다. → P0 에서 v1 샘플 · 파서 확인 완료 (4장).
-   구형 파일은 원본을 백업(사용자 컴퓨터의 원본 유지)한다.
-   v2.1 의 'import 가능하면 `schema_version=legacy` 로 읽고 누락된 경험 ID/버전은 안전하게 생성·표시'는 실제 v1 형식(`version: 1`)에 맞게 4장으로 대체했다. 경험 ID/버전 생성은 v1 의 '내 경험' 글을 2차 경험 카드로 옮길 때(M1) 검토한다.
-   'import 불가능하면 구형 이어하기 기능을 임시 유지하고 새 저장 방식과 차이를 안내'는 v1 읽기 호환 유지로 충족한다.
-   새 export 가 기존 import 와 호환된다고 가정하지 않는다.

## 9. 팀 결정 필요 (2차)

-   선택 저장 UX
-   2차 저장 방식: 실제 DB 또는 파일 저장소, 자동 저장 주기 · 오프라인 정책
-   지원 상태 단계 (기존 요구사항 후보 `준비 → 지원 → 대기 → 면접 → 결과`)

-   진행 중 미제출 초안 export 기본 정책
-   (확정) 1차 저장 방식은 Markdown 수동 백업, 평가위원 4명 유지, v1 import 는 4장 범위

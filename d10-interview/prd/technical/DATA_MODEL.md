# 데이터 모델 및 Markdown 내보내기 명세

> 기준: PRD v2.3 (0.4 · 0.5 · 0.6 · 5.6 · 8.1).  
> 0장은 **1차 MVP 확정 구조**다. 1장 이후는 2차 MVP까지 포함한 목표 모델이며, 2차 범위에는 **[2차 MVP]** 를 표시한다.  
> 이 문서는 목표 구조다. 현재 코드(v1 리포트, 회차 1개 = 파일 1개)와의 차이와 전환은 `../MIGRATION.md` 를 본다.

## 0. 1차 MVP 데이터 구조 (확정)

### 0.1 식별자

| 대상 | 필드 | 규칙 |
|---|---|---|
| 회사 | `company_id` | 회사 고유 식별자. 회사명과 별도로 생성한다 |
| | `company_name` | 사용자에게 보여 주는 회사명 (입력 그대로) |
| | `company_key` | 같은 회사 판단용 키. 회사명의 **앞뒤 공백만 제거**하고, 중간 공백과 대소문자는 바꾸지 않는다. `company_key` 가 정확히 같으면 같은 회사 |
| 회사 미지정 | (미확정) | 회사를 지정하지 않은 면접은 화면에서 **'기타'** 그룹으로 보여 준다. 실제 회사명 '기타'와 구분하고 회사 데이터로 취급하지 않는다. 내부 식별 방식은 P1 데이터 모델 구현 전에 정한다 |
| 직군(직무) | `job` | 회사(또는 '기타') 아래 직군별로 회차를 나눈다 |
| 회차 | `round_id` | 회차 고유 식별자 |
| | `round_number` | 사용자에게 보여 주는 회차 번호. 같은 **회사(또는 '기타') + 직군(직무)** 안에서 누적하며 공통 · 분야별 면접이 같은 번호 체계를 쓴다. 재도전으로 늘지 않는다 |
| 질문 | `question_id` | `Q0001` 형식의 영구 ID. 바꾸거나 다시 쓰지 않고, 질문 문구 · 분류가 바뀌어도 유지한다. 새 질문은 새 ID |
| 재도전 | `attempt_id` | 재도전 기록 하나의 고유 식별자 |

-   면접 기록은 회사명이 아니라 `company_id` 로 연결한다. 회사명 변경 UI는 2차지만, 변경해도 연결이 유지되는 구조다.
-   ID 생성 방식(임의 값 · 결정적 값 등)과 v1 기록의 안정적 ID 매핑 방식은 **미확정**이다 (PRD 10.2). 단, 같은 v1 기록을 반복해 불러와도 같은 회차로 식별되어야 한다.
-   질문 ID 실제 부여(질문 은행 CSV 수정)는 P1 구현 단계에서 한다.

### 0.2 회차 레코드 (1차)

회차 하나는 아래 정보를 가진다. 필드 이름 · 세부 형태는 P1 설계에서 확정한다.

| 묶음 | 내용 |
|---|---|
| 식별 | `round_id`, `company_id`(회사 미지정이면 없음 · '기타' 그룹), `job`, `round_number`, 날짜 |
| 면접 설정 | 면접 유형(공통 / 분야별), 분야, 질문 출제 방식, 면접관 정보 |
| 질문 | 질문마다 `question_id` · **당시 질문 문구** · 유형 · 분야 (현재 질문 은행에 없는 과거 질문은 0.5) |
| 면접 기록 | 질문 · 원본 답변 · 꼬리질문 · 면접관 반응 (메시지마다 확장 정보 칸을 두어 2차의 '참고한 경험' 등을 더할 수 있게 한다) |
| 원본 답변 | 질문별 최초 답변 (재도전과 구분) |
| 평가 | 위원별 평가 · 위원 평균 의견 · 답변별 기준 점수 · 약한 점 · 다듬은 답 · 확인할 사실 · 다음에 고칠 것 |
| 처리 상태 | 기능별 처리 상태 (예: 평가 완료 / 실패). 2차의 AI 초안 생성 상태를 같은 방식으로 더할 수 있게 한다 |
| 재도전 | 0.3 의 재도전 기록 목록 |

-   회차의 질문 · 답변 · 평가는 독립적으로 저장하며, 새 회차가 기존 회차를 덮어쓰지 않는다.
-   평가 결과는 당시 질문 문구 · 답변과 함께 보존하고 이후 다시 계산하지 않는다.

### 0.3 재도전 기록 (1차)

| 필드 | 내용 |
|---|---|
| `attempt_id` | 재도전 기록 고유 ID |
| `round_id` · `question_id` | 어느 회차 · 질문의 재도전인지 |
| 답변 | 제출한 재도전 답변 |
| 평가 | 제출 시점 답변의 기준 점수 · 약한 점 |
| 시각 | 제출 시각 (선택) |

-   재도전은 새 회차가 아니라 기존 회차의 답변 개선 이력이다.
-   **횟수 제한이 없다.** 재도전 횟수 제한을 위한 별도 카운터를 v2에 저장하지 않는다. 재도전 순서 · 횟수는 저장된 기록으로 계산한다.
-   원본 답변과 기존 재도전 기록을 삭제하거나 덮어쓰지 않는다. 새 답변 · 평가는 새 기록으로 누적한다.
-   종합 점수에 반영할 점수(같은 회차 · 질문의 최고 점수)는 기록에서 계산하며 따로 저장하지 않아도 된다.

### 0.4 Markdown v2 (1차)

-   **파일 하나에 여러 회사 · 직군 · 회차**를 담는다 (전체 기록 저장). 회사 미지정('기타') 회차도 함께 저장한다.
-   파일 = 사람이 읽는 Markdown 본문 + 복원용 데이터.
-   복원용 데이터는 기존과 같은 `interview-data` 태그의 숨은 주석에 JSON 으로 넣고, `version: 2` 를 쓴다. (v2.2 예시의 front matter `schema_version` 표기는 쓰지 않는다.)
-   최상위에는 버전과 회사 · 회차 목록을 두고, 2차에서 경험 · 취업 관리 항목을 더할 수 있도록 모르는 항목은 읽을 때 무시한다.
-   저장은 새 파일 다운로드이며 기존 파일을 자동으로 덮어쓰지 않는다.
-   과거 면접 · 평가 · 재도전 기록은 저장 · 복원 후에도 당시 상태를 유지한다.

### 0.5 불러오기 · 호환 (1차)

| 형식 | 처리 |
|---|---|
| v2 | 회사 · 회차 · 재도전 기록을 복원한다 |
| v1 (`interview-data` · `version: 1`, 회차 1개 = 파일 1개) | 읽기 호환을 유지한다. 회차 레코드로 변환한다 (지원 · 부분 복원 · 거부 형식은 `../MIGRATION.md`) |
| 그 밖의 버전 | 지원하지 않는 형식으로 안내하고 안전하게 거부한다 |

-   v1 의 재도전 기록은 v2 재도전 기록으로 옮기고 `attempt_id` 를 부여한다. v1 의 재도전 횟수 칸(`retry_counts`)은 제한용 카운터라 v2 에 저장하지 않는다.
-   **현재 질문 은행에 없는 과거 질문:** 당시 질문 원문 · 최초 제출 답변 · 기존 평가 결과 · 재도전 답변과 평가 이력 · 기록의 연결 관계를 보존한다 (확정). 이 질문에도 기존 원문으로 재도전할 수 있고, 과거 평가는 수정하거나 다시 계산하지 않으며, 다른 질문에 임의로 연결하지 않는다 (확정). 질문 ID 매핑에 실패한 질문의 내부 식별 · ID 생성 · 변환 · 저장 방식은 **미확정**(P1 에서 결정)이며, `Q0001` 영구 질문 ID 정책과 충돌하지 않게 정한다.
-   같은 기록을 반복해 불러와도 회차가 중복 생성되거나 기존 기록이 자동으로 덮어써지지 않는다. 같은 `round_id` 인데 내용이 다른 경우의 처리 방식은 미확정이다 (PRD 10.2).
-   Markdown 복원 자체는 새 회차를 만들지 않는다.

### 0.6 선택 저장 [2차 MVP — 방향만 확정]

선택 저장은 향후 확장 방향으로 유지한다. 저장 단위 · 화면 구성 · 선택 방식 · 저장 대상 제외 방식 · 저장 전 확인 절차 · 선택 저장과 삭제의 관계는 **미확정**이다. 1차 구조는 이 확장을 막지 않도록 회차 단위로 독립된 레코드를 두되, 선택 저장 기능을 1차에서 구현하지 않는다.

### 0.7 1회차 리포트 개정 (E-5, 구현됨)

여러 회차를 담는 v2(0.4) 전에, 지금의 1회차 = 파일 1개 리포트에 칸을 더해 답변 · 평가 보존을 보강했다.

-   형식: `interview-data` 숨은 데이터의 `version: 1` 을 유지하고 `revision: 2` 를 더한다. 옛 앱은 모르는 칸을 무시하고 읽으며, 새 앱은 `revision` 이 없는 v1 파일도 읽는다.
-   더한 칸 (`session` 안, 값이 있을 때만 저장):

| 칸 | 내용 |
|---|---|
| `retry_history[질문][].attempt_id` | 재도전 기록 ID `q{질문}-a{n}`. 없는 v1 기록은 읽을 때 순서로 붙이며, 같은 파일은 늘 같은 ID 가 나온다. 새 기록은 그 질문에서 쓴 가장 큰 번호 + 1 |
| `latest_unscored{질문: {answer}}` | 채점받지 못한 최신 제출 답. 이미 채점받은 답(면접 때 답 · 재도전 기록)과 같은 글이면 저장하지 않는다. 점수 계산에 넣지 않는다 |
| `retry_unreadable{질문: [{attempt_id, raw}]}` | 읽지 못한 재도전 기록의 원본. 점수 계산에 넣지 않고, 다시 저장해도 그대로 남긴다 |
| `evaluation_unreadable[]` | 읽지 못해 다시 평가받기 전의 최초 평가 원본 |

-   세 가지 답:
    -   **최초 답:** 면접 기록(`messages`)의 답과 최초 평가(`evaluation`). 재도전으로 덮어쓰지 않는다.
    -   **최고 점수 답:** 최초 점수보다 높은 재도전 중 가장 높은 것, 동점이면 먼저 받은 것. 따로 저장하지 않고 기록에서 계산한다 (옛 앱 호환을 위해 `retries` 칸은 계속 쓰지만 읽을 때는 쓰지 않는다).
    -   **최신 제출 답:** 마지막 제출이 채점에 실패했으면 `latest_unscored`, 성공했으면 `retry_history` 의 마지막 기록.
-   재도전 횟수는 기록 개수로 계산한다. `retry_counts` 칸은 옛 앱 호환을 위해 같은 값을 계속 쓰지만 읽을 때는 쓰지 않는다.
-   읽기 검증: 최초 평가와 재도전 기록은 AI 응답과 같은 검증을 거친다 (`AI_RULES.md` 4장). 범위 밖 정수 점수는 경계값으로 보정한다.
    -   최초 평가가 검증에 실패하면 0점으로 채우지 않고 질문 · 답(과 재도전 기록)만 불러온다 (부분 복원). 사용자는 다시 평가받을 수 있고, 원본은 `evaluation_unreadable` 로 다음 저장에 남는다.
    -   읽지 못한 재도전 기록은 원본을 `retry_unreadable` 로 보존하고 점수 · 횟수 계산에서 뺀다.
    -   안내: "평가 데이터를 읽지 못해 질문과 답변만 불러왔어요. 다시 평가받을 수 있어요." / "일부 재도전 평가를 읽지 못했어요. 답변은 보존했지만 해당 점수는 반영하지 않았어요." 오류 기록은 `restore_validation` · `restore_parse` (문제 코드 · 개수만).
-   안전 한도: 파일 5MB, 질문당 재도전 기록 500개. 넘으면 일부만 읽지 않고 불러오기 전체를 거부하고 이유를 안내한다. 재도전 기록 목록은 다른 목록의 40개 한도로 자르지 않는다.
-   불러오기에 실패해도 올린 원본 파일과 지금 세션은 바꾸지 않는다. 저장은 늘 새 파일 다운로드다.
-   세션에만 있는 것 (파일에 남지 않음): 면접 중 전달하지 못한 답, 암기 탭에서 쓰던 대본, 암기 탭 검토와 재도전 기록의 연결(`attempt_id` 기준). 1차는 자동 저장이 없으므로 리포트를 받기 전에 브라우저를 닫으면 사라진다 (3장). 리포트는 최초 평가가 있어야 받을 수 있다.

**회사 미등록 면접 (1차 확정)**

-   `InterviewRound.company_id` 는 선택값이다. 회사를 지정하지 않은 회차는 화면에서 '기타' 그룹으로 보여 준다 (0.1).
-   회사 미지정 상태를 실제 `Company` 데이터로 취급하지 않으며, 실제 회사명이 '기타'인 `Company` 와 구분한다.
-   회사 미지정 그룹의 내부 식별 방식(예: 비어 있는 값 · 별도 표시 등)과, 미지정 회차를 나중에 특정 회사로 옮기거나 연결하는 기능은 **미확정**이다 (PRD 10.2).

-   v2.2 의 `Company.role` 은 회사와 회사·직군을 구분하는 PRD 5.5 에 맞게 `Company` / `CompanyRole` 로 나눴다.
-   v2.2 의 `InterviewSession` 은 회차(`InterviewRound` · `round_id`)로 이름을 맞췄다. 1차 평가는 회차 단위(위원별 평가 + 답변별 점수)다.
-   AI 경험 카드 초안 엔터티와 상태(검토 대기 / 저장 완료 / 저장하지 않음)는 PRD 5.2 에 따라 2차에서 정의한다.

## 2. 버전/평가 보존 (`DATA-01`)

-   경험 수정은 새 ExperienceVersion 생성 후 카드의 `current_version`
    갱신. [2차 MVP]
-   InterviewAnswer는 **답변 제출 당시**의 `experience_version` 참조. [2차 MVP]
-   Evaluation에는 질문(당시 문구), 답변 텍스트, 평가 루브릭 버전의
    스냅샷 저장. 경험 정보 스냅샷은 2차에서 기록용으로 저장하며 평가 근거로 쓰지 않는다.
-   이후 경험 수정, 질문 태그 · 문구 변경, 평가 모델 변경이 과거 결과에 영향을
    주지 않음.
-   재평가 시 새 Evaluation 생성; 기존 결과 덮어쓰기 금지. 재도전 평가는 RetryAttempt 로 누적한다.

## 3. 작업 데이터와 파일 저장 구분 (`DATA-02`)

-   **작업 데이터:** 사용자가 현재 화면에서 작업 중인 데이터. **1차 MVP**는 서비스 내부 영속 저장 · 자동저장을 두지 않으며, 브라우저 · 세션 종료 시 백업하지 않은 데이터는 사라질 수 있다 (PRD 5.6).
-   **Markdown 저장:** 사용자가 실행하는 파일 다운로드(수동 백업).
-   **Markdown 불러오기:** v2 와 v1 의 복원은 1차 MVP 범위다 (0.5). (v2.2 의 '새 형식 역직렬화는 P1로'는 이 원칙으로 바꿨다.)
-   **2차 MVP 저장 방식은 미확정이다.** v2.2 의 '내부 저장: 사용자 작업 상태를 유지하는 영속 저장(구현 방식 팀 결정)'과 '`.md` 다운로드가 앱 내부 저장을 대신하지 않는다'는 2차 설계 시 검토할 요구사항 후보로 보존한다 (8장).

## 4. 내보내기 유형 [2차 MVP — 1차는 0.4 의 전체 기록 v2 저장 하나]

  ---------------------------------------------------------------------------------------
  ID                모드              포함                              허용 시점
  ----------------- ----------------- --------------------------------- -----------------
  `EXPOR-01`        경험 관리만       프로젝트, 경험 카드,              면접 0건/작성
                                      버전·상태·태그, 선택적 퀘스트     중에도

  `EXPOR-02`        경험+면접 통합    경험 데이터 +                     면접 전·중·후
                                      회사/회차/질문/답변/평가/퀘스트   

  `EXPOR-03`        면접만            회사 · 회차 · 질문 · 답변 ·       1차: 전체 기록
                                      평가 · 재도전                     (진행 중 회차 포함
                                                                        여부는 미확정)
  ---------------------------------------------------------------------------------------

-   `EXPOR-03` 의 범위는 1차의 전체 기록 v2 저장이 담는다.
-   범위 선택은 **2차 MVP의 기존 요구사항 후보**로 보존한다: 경험만 내보내기는 경험 전체 / 프로젝트별, 통합 내보내기는 전체 / 회사별 / 회차(세션)별. 선택 저장의 구체적인 단위 · UX · 확인 절차는 미확정이며, 이 후보를 확정된 UX로 보지 않는다.

## 5. 공통 출력 규칙 (`EXPOR-04`)

-   UTF-8 `.md`, ISO 8601 내보낸 시각, 원본 ID.
-   복원용 데이터는 `interview-data` 숨은 주석의 `version` 으로 형식을 구분한다 (1차: `version: 2`).
-   export mode 표기와 범위 선택은 [2차 MVP].
-   파일명 규칙은 미확정이다. (v2.2 예: `yeokjeon-experiences-2026-11-01.md`, `yeokjeon-full-company-2026-11-01.md` · 현재 v1: `yymmdd-회사-직군-n회차-면접리포트.md`)
-   빈 필드는 `미작성`, 진행 중 회차는 `진행 중`, 평가 전은 `평가 대기`
    표시.
-   미제출 답변 초안은 기본 제외; 포함 시 '미제출 초안' 명시하고 사용자
    동의. (진행 중 면접 저장이 확정될 때 적용)
-   중복 경험은 통합 문서의 경험 섹션에 한 번만 기록하고 답변에서 ID로
    참조. [2차 MVP]
-   Markdown 텍스트에 포함된 특수 문자·사용자 입력 제목은 안전하게
    이스케이프/정규화.
-   다운로드 전에 개인정보 포함 여부를 보여준다. (선택 범위 표시는 2차)
-   내보내기 실패는 작업 데이터에 영향을 주지 않는다.

## 8. 저장 정책 결정 사항

**1차 MVP**

-   (확정) 서비스 내부 DB · 자동저장 없이 Markdown 수동 백업. 이 확정은 1차 MVP에만 적용한다.
-   (확정) v1 import 호환 범위 (`../MIGRATION.md`).
-   ID 생성 방식과 v1 기록의 안정적 ID 매핑 방식 (미확정).
-   질문 ID 매핑에 실패한 과거 질문의 내부 식별 · 변환 방식 (미확정, P1).
-   회사 미지정('기타') 그룹의 내부 식별 방식, 미지정 기록의 회사 연결 · 이동 (미확정).
-   같은 `round_id` 의 내용이 다른 기록을 불러올 때의 처리 (미확정).
-   진행 중 면접 저장 · 재개 (미확정).
-   내보내기 파일 암호화 여부(기본 Markdown은 암호화되지 않음).

**2차 MVP (설계 시 검토)**

-   실제 DB 또는 파일 저장소 선택.
-   자동저장 주기 및 오프라인 동작.
-   선택 저장 UX 전반 (미확정).
-   소프트 삭제 및 개인정보 보존 기간.

## 9. 완료 기준

**1차 MVP**

-   여러 회사 · 직군 · 회차를 v2 파일 하나로 저장하고 다시 불러오면 회차 · 질문(ID · 당시 문구) · 원본 답변 · 평가 · 재도전 기록이 그대로다.
-   기존 v1 파일을 불러올 수 있다 (지원 형식).
-   같은 파일을 반복해 불러와도 회차가 중복 생성되지 않는다.
-   재도전 기록이 횟수 제한 없이 누적되고, 원본 답변 · 기존 평가가 바뀌지 않는다.
-   회사 미지정('기타') 회차와 현재 질문 은행에 없는 과거 질문도 저장 · 복원 후 그대로다.
-   파일 재열람 시 ID, 상태, 질문·답변 관계를 식별 가능.

**2차 MVP**

-   면접 없는 경험 데이터의 단독 내보내기 성공.
-   진행 중 면접 포함 통합 내보내기 성공 (진행 중 저장이 확정되면).
-   내보내기 후에도 편집 중 데이터 불변.
-   경험 수정 후 이전 평가 스냅샷 유지.
-   파일 재열람 시 경험 카드 버전까지 식별 가능.

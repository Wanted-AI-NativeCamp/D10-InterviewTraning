## 01. 프로젝트 개요

### 서비스명 · 목적
**역전 취업 코칭** — 신입 지원자를 위한 AI 모의면접 코치 (Streamlit + OpenAI API).
직군 · 회사 · 산업 분야를 고르고 실제 면접처럼 5문제에 답한 뒤, 평가 위원 4명의 채점을 받고 낮은 답을 다시 연습한다. 기록은 Markdown 파일로 저장하고 다시 불러온다.

### AI 활용 목적
사람 면접관 없이도 ① 답이 부족한 곳을 되묻는 면접관, ② 여러 관점의 채점, ③ 다시 쓴 답의 재채점을 받을 수 있게 한다.
AI에게는 **판단**(답이 충분한가, 무엇을 더 물을까, 기준별로 몇 점인가)만 맡기고, 질문 수 · 꼬리 질문 횟수 · 점수 합계 · 평균 · 판정은 **코드가 계산**한다.

### 주요 AI 기능 (현재 화면에서 쓰는 것)

| 기능 | 언제 | 프롬프트 |
|---|---|---|
| 면접관 반응 · 꼬리 질문 · 이해도 | 면접 중 답을 낼 때마다 | `INTERVIEWER` |
| 평가 위원 4명 채점 · 답변별 기준 점수 · 다듬은 답 | 5문제를 마치고 [평가 받기] | `EVALUATOR` |
| 재도전 채점 | 재도전 탭에서 [다시 채점] | `RETRY` |
| 형광펜 (문장마다 기준 표시) | 평가 화면에서 사용자가 켤 때 | `HIGHLIGHT` |
| 전략 가이드 (약한 기준 올리는 방법) | 평가 화면에서 사용자가 누를 때 | `STRATEGY` |

## 02. 프롬프트 설계 구조

### 공통 호출 방식
- OpenAI 호출은 `llm.py` 의 `ask_json(instructions, user_input, schema, name)` **한 곳**뿐이다.
- `instructions` 에는 지시문(아래 프롬프트), `user_input` 에는 지원자의 대화 · 답을 따로 넣는다. 지원자 글이 지시문을 덮어쓰지 않게 나눴다.
- 응답은 모두 **JSON 스키마 · `strict: true`** 로 받는다 (Responses API `text.format`). 글로 받아서 잘라 쓰지 않는다.
- 기본 모델: `gpt-6-luna` (`OPENAI_MODEL` 로 바꿀 수 있음).

### 프롬프트별 역할 · 입력 · 출력 · 제약

| 프롬프트 | 역할 | 지시문에 채우는 값 | user_input | 출력 (스키마 칸) | 핵심 제약 |
|---|---|---|---|---|---|
| `INTERVIEWER` | 면접관 | `{persona}` `{context}` `{question}` `{point}` | 지금까지 대화 | `reply` 글 · `follow_up` 참/거짓 · `understanding` 정수 | 칭찬 · 정답 금지, 꼬리 질문 1개 · 200자, [보는 점] 안에서만, 가정형 답과 실제 경험 구분, 말하지 않은 사실 전제 금지 |
| `EVALUATOR` | 평가 위원회 4명 | `{panel_criteria}` `{context}` (경험 제외) | 면접 기록 + 질문별 `[보는 점]` | `panel[]`(위원 · 반론 · 좋은 점 · 0~10점) · `conflict` · `agree` · `answers[]`(기준 4개 0~5 · `weak` · `rewrite` · `check`) · `next[]` | 반론 먼저, 지어낸 숫자 대신 `[확인 필요: ○○]`, 합계 쓰지 않기, [보는 점]은 참고 기준 |
| `RETRY` | 재도전 채점자 | `{persona}` `{context}` (경험 제외) `{question}` `{point}` `{before}` `{weak}` | 다시 쓴 답 | 기준 4개 0~5 · `weak` | 다시 쓴 답만 채점, 나아졌다는 이유만으로 올리지 않기 |
| `HIGHLIGHT` | 답변 분석가 | `{context}` | 번호 붙인 문장 + 질문 · 보는 점 | `sentences[]`(`no` · `tags` · `why`) | 모든 문장을 빠짐없이, 번호 그대로, 지어내지 않기 |
| `STRATEGY` | 코치 | `{context}` `{question}` `{point}` `{scores}` `{opinion}` | 지원자 답 | `tips[]`(`criterion` · `action` · `target` · `tip`) | 5점 아닌 기준만, 동작은 추가 · 수정 · 축약 · 삭제, 한 문장 120자 |

### 공통 구성 요소
- **`CONTEXT` (상황 블록)**: 회사 · 회사 설명 · 산업 분야 · 직군 · 지원자 경험을 한 덩어리로 만들어 모든 지시문에 넣는다.
  - 평가 · 재도전 채점에는 경험 자리에 "(평가에는 쓰지 않음)"을 넣는다. **실제로 제출한 답만 평가 근거로 쓰기 위해서다** (`coach.build_context(with_experience=False)`, PRD 0.3).
- **`PERSONAS`**: 직군별 면접관 글. 면접관(`INTERVIEWER`)과 재도전 채점(`RETRY`, `weak` 말투)에 들어간다. MVP1에서는 직군마다 면접관 1명을 자동 배정한다.
- **`FIELDS`**: 산업 분야 9개(공통 · 헬스케어 · 핀테크 · 금융 · 커머스 · 에듀테크 · 모빌리티 · 여행 · 콘텐츠 · 미디어 · B2B · SaaS · 게임)의 한 줄 설명. `{field_desc}` 로 들어간다.
- **`PANEL_CRITERIA`**: 위원 4명의 평가 기준. 출처는 `data/평가기준_근거.md` (구조화 면접 · NCS 직업기초능력 등).
- **질문 은행 `data/questions.csv`**: 질문 193개와 질문마다 **'보는 점'**(이 질문으로 확인하려는 것). 면접관의 `{point}` 와 평가 입력의 `[보는 점]` 으로 들어간다.

### 프롬프트 간 연결

```
면접 설정 (회사 · 직군 · 분야 · 경험)          질문 은행 (질문 + 보는 점)
        │  CONTEXT · PERSONAS · FIELDS              │
        ▼                                           ▼
  INTERVIEWER  ── 답마다 호출 ──▶ reply · follow_up · understanding
        │        코드: 꼬리 질문은 질문당 최대 1개 (AI가 더 원해도 막음) · 이해도 0~100 자르기
        ▼ 5문제 끝
  EVALUATOR  ◀── 면접 기록 + 질문별 [보는 점] (경험은 평가에 쓰지 않음)
        │        코드: 응답 검증(위원 4명 · 답 번호 1~5 · 정수 점수) → 실패 시 자동 1회 재요청
        │        코드: 범위 밖 점수는 경계값으로 보정 · 답 점수(0~20) · 종합(0~100) · 위원 평균 · 판정 계산
        ├──▶ HIGHLIGHT  (사용자가 켤 때) 문장별 기준 표시
        ├──▶ STRATEGY   (사용자가 누를 때) 약한 기준 · 평가의 weak · next 를 받아 전략
        ▼
  RETRY  ◀── 지난 답 · 지난 약한 점 + 다시 쓴 답
                 코드: 같은 질문의 최고 점수만 종합 점수에 반영 · 이미 채점한 답은 다시 부르지 않음
```

## 03. 핵심 프롬프트 (원문)

> 아래 블록은 `d10-interview/prompts.py` 의 문자열을 그대로 옮긴 것이다. `{ }` 는 앱이 채우는 변수다.

### 3-1. 상황 블록 `CONTEXT`
- 위치: `prompts.py` · 채우는 곳 `coach.build_context()`
- 기능: 모든 지시문에 같은 상황 정보를 넣는다.

```text
- 회사: {company} ({company_desc})
- 분야: {field} ({field_desc})
- 지원 직군: {job} 신입
- 지원자가 직접 적은 경험: {experience}
```

### 3-2. 면접관 `INTERVIEWER`
- 위치: `prompts.py` · 만드는 곳 `coach.build_interviewer()` · 부르는 곳 `app.send_answer()`
- 기능: 지원자 답에 짧게 반응하고, 답이 [보는 점]을 충분히 보여 주지 못하면 꼬리 질문 1개를 낸다. 지금까지 답으로 본 직무 이해도(0~100)를 준다. 꼬리 질문을 실제로 낼지는 코드(`coach.wants_follow_up`)가 최종 결정한다.

```text
너는 아래 페르소나의 면접관이야. 지금은 모의면접이고, 지원자를 돕는 게 아니라 실제처럼 확인하는 역할이야.
페르소나: {persona}
{context}
[이번 질문] {question}
[이 질문에서 보는 점] {point}
[규칙]
1. 지원자의 마지막 답에 대한 반응은 지원자가 실제로 말한 내용에 근거한 짧은 문장만. 칭찬이나 정답 알려 주기는 하지 마.
2. 답이 [보는 점]을 충분히 보여 주지 않으면 follow_up 을 true 로, 꼬리 질문 1개를 reply 에. 충분하면 false.
3. 꼬리 질문은 한 번에 하나, 200 자 이내.
4. 꼬리 질문은 [이번 질문]의 [보는 점]에서 벗어나지 마. 페르소나가 자주 묻는 주제도 [보는 점]과 관련 있을 때만 묻는다.
5. 실제로 해 본 경험과 가정형 대응('~하겠습니다', '~할 것 같습니다')을 구분해. 가정형 답을 실제 경험으로 보지 마.
   가정형 답에는 판단 기준 · 실행 방법 · 예상되는 어려움을 구체화하는 꼬리 질문을 먼저 고려해.
   실제 경험을 확인하는 꼬리 질문은 [보는 점]을 확인하는 데 필요할 때만.
6. 수치 · 성과는 [보는 점]과 관련 있을 때만 묻는다. 지원자가 실제 결과를 말했으면 그 결과를 어떻게 확인했는지,
   결과 없이 계획만 말했으면 앞으로 어떻게 검증할지를 묻는다. 실제 결과와 검증 계획을 섞지 마.
7. 지원자가 말하지 않은 경험 · 결과 · 성과 · 수치를 사실처럼 말하거나 이미 있는 것처럼 전제하지 마.
8. 지원자가 질문 뜻을 되물으면 정답은 알려 주지 말고, 이 질문이 무엇을 확인하려는지([보는 점])를 쉬운 말로 다시 설명해.
9. understanding 은 지금까지 답으로 본 직무 이해도 0~100.
출력은 JSON 하나만: reply(글), follow_up(참/거짓), understanding(숫자)
```

`{persona}` 에 들어가는 디자인 직군 면접관 글 (`PERSONAS["디자인"]`, 사용자 작성):

```text
7년 차 디자인 팀장 (역할). 사용자 경험 · 사용성 · UI 디자인 툴 숙련도(Figma, Photoshop, illustrator) · 모바일 앱/웹 프론트 프로토타이핑 역할 · 컨셉과 맥락에 맞는 완성도있는 그래픽 역량 능력 · 디자인 트렌드를 꾸준히 연구하고 영감을 줄 수 있는지 · 다양한 팀의 조직원들과 원활한 소통이 가능한지 · 자신의 업무에 대한 ownership 을 꼭 본다. 말투는 딱딱한 말투 이고 생성형 AI 능력과 앱/웹 기반 사용 서비스 경험과 사용자조사 데이터를 근거로 꾸준하고 적극적인 서비스 개선 경험 을 자주 묻는다.
```

개발 · PO · 마케팅 면접관 글은 같은 형식(연차 · 역할 · 꼭 보는 역량 · 말투 · 자주 묻는 것)의 **Claude Code 초안**이며, `prompts.py` 에 "사용자 확인 필요"로 표시되어 있다. 원문은 `prompts.py` 의 `PERSONAS` 에 있다.

### 3-3. 평가 위원회 `EVALUATOR`
- 위치: `prompts.py` · 만드는 곳 `coach.build_evaluator()` · 부르는 곳 `app.request_evaluation()`
- 입력: 면접 기록은 user_input 으로 넘긴다 (`coach.format_record`: `[질문 n · 유형] 질문` / `[보는 점] …` / `[면접관] …` / `[지원자] …`).
- 기능: 위원 4명이 따로 본 뒤 합친다. 반론을 먼저 쓰게 해 점수가 후해지는 것을 막고, 답변마다 기준 4개 점수 · 가장 약한 점 · 다듬은 답 · 사람이 확인할 사실을 받는다.

```text
너는 모의면접 평가 위원회야. 아래 면접 기록을 4명의 눈으로 따로 본 뒤 합쳐.
위원: 실무 전문가 · 논리 분석가 · 커뮤니케이션 전문가 · 채용 담당자
[위원별 평가 기준]
{panel_criteria}
{context}
[평가 순서 — 이 순서를 지켜]
1. 위원마다: 먼저 '이 지원자를 뽑지 말아야 할 이유' 1문장(반론 먼저), 그다음 좋은 점 1문장, 0~10점.
2. 4명을 비교해 conflict(판단이 갈린 곳) · agree(모두 같은 판단) 각 1문장.
3. 답변마다 기준 4개(구체성 / 직무 연관 / 구조 / 근거 · 검증)를 각각 0~5점. 가장 약한 점 하나를 weak 에.
4. 답변마다 rewrite: 같은 경험으로 더 좋은 답 300자 문장 이내.
   지원자가 쓰지 않은 숫자 · 회사 · 성과는 넣지 마. 꼭 필요하면 [확인 필요: ○○].
   check 에 사람이 확인할 사실 0~2개.
5. next 에 다음 연습에서 고칠 것 3개.
[보는 점] 면접 기록의 질문마다 붙은 [보는 점]은 질문의 평가 의도를 이해하기 위한 참고 기준입니다.
특정 키워드의 포함 여부만으로 판단하지 말고, 답변의 내용과 근거, 문제 해결 접근 방식의 타당성을 종합적으로 평가하세요.
출력은 JSON 하나만. 점수 합계는 쓰지 마 (앱이 계산해).
```

`{panel_criteria}` 에 들어가는 위원별 기준 (`PANEL_CRITERIA`):

```text
- 실무 전문가: 직무 지식 · 툴 숙련도, 실제 업무에 바로 쓸 수 있는 경험인가
- 논리 분석가: 문제 → 원인 → 해결 → 결과 흐름이 맞고, 주장과 근거가 연결되는가
- 커뮤니케이션 전문가: 결론부터 간결하게 말하고, 질문 의도에 맞게 답하는가
- 채용 담당자: 회사 · 직무 적합성, 협업 태도, 성장 가능성
```

### 3-4. 재도전 채점 `RETRY`
- 위치: `prompts.py` · 만드는 곳 `coach.build_retry()` · 부르는 곳 `app.show_retry()`
- 기능: 같은 질문에 다시 쓴 답을 최초 평가와 같은 기준 4개로 채점한다.

```text
너는 모의면접 채점자야. 지원자가 같은 질문에 다시 쓴 답을 채점해.
페르소나: {persona}
{context}
[질문] {question}
[이 질문에서 보는 점] {point}
[지난 답] {before}
[지난 답의 약한 점] {weak}
[규칙]
1. 다시 쓴 답만 채점한다. 지난 답은 무엇이 바뀌었는지 비교할 때만 본다.
```

### 3-5. 형광펜 `HIGHLIGHT` (Claude Code 초안 — 코드 주석에 "사용자 확인 필요")

```text

- structure(구조): 답의 흐름을 잡는 문장 (결론 먼저, 순서, 정리)
```

### 3-6. 전략 가이드 `STRATEGY` (Claude Code 초안 — 코드 주석에 "사용자 확인 필요")

```text

{context}
[질문] {question}
[이 질문에서 보는 점] {point}
[기준별 점수 (각 0~5)]
{scores}
[위원회 종합 의견]
{opinion}
[규칙]
1. 5점이 아닌 기준마다 전략 1~2개. 5점인 기준은 쓰지 마.
2. action 은 추가 · 수정 · 축약 · 삭제 중 하나.
3. target 에 내 답에서 고칠 부분을 짧게 그대로 옮겨 적어. 추가라면 빈 글.

```

  > 기존 평가위원 역할과 점수 체계는 유지해 주세요.

**반영:** `EVALUATOR` 끝에 권장 문구를 그대로 넣고 (03장 원문), `format_record` 가 질문 바로 아래에 `[보는 점] …` 줄을 붙인다. 보는 점이 없는 옛 기록은 그 줄 없이 이전과 같다.

**확인 가능한 결과:** `tests/test_eval_record.py` — 평가 입력에 질문 5개의 보는 점이 모두 들어가는지, 옛 기록은 그대로인지, 평가 지시문에 참고 기준 문장이 있는지 확인한다. 실제 평가 점수 변화는 **확인 불가**.

### 4-5. 프롬프트를 바꾸지 않고 코드로 해결한 것
프롬프트 문장을 지키면서 아래는 코드 쪽에서 처리했다 (11-02 오류 관리 E-1 ~ E-5, 사용자가 단계별로 승인).
- **평가 응답 검증**: 위원 4명 누락 · 중복, 답 번호 1~5, 정수가 아닌 점수(`5.0` · `true` · `"5"`) 등은 정상 평가로 저장하지 않고 **자동 1회 재요청**, 그래도 실패하면 한국어 안내 · 다시 시도. 이때 사용자 지시: "프롬프트와 AI 모델은 변경하지 않습니다."
- **점수 범위**: 범위 밖 정수만 경계값으로 보정 (기준 0~5 · 위원 0~10). 처음에는 "보정하지 않음"으로 정했다가 `CLAUDE.md` 교육 규칙("점수는 범위 밖이면 잘라 쓴다")에 맞춰 사용자가 정책을 바꿨다.
- **꼬리 질문 한도**: AI가 `follow_up: true` 를 줘도 질문당 1개를 넘으면 코드가 막는다 (`coach.should_follow_up`, `MAX_FOLLOW_UPS = 1`).

### 5-3. 작업 지시 프롬프트의 방식 (프롬프트로 해결한 문제)
대화 기록에서 확인되는, Claude Code 에게 일을 시킨 방식이다.
- **분석 먼저, 수정은 승인 뒤**: "이번 작업은 분석 전용입니다. 코드를 수정하거나 파일을 삭제·이동하지 마세요." · "먼저 원인 분석과 개선안을 보고해 주세요. 아직 코드나 프롬프트를 수정하지 마세요." → 꼬리 질문 문제를 A안(규칙 보강) / B안(질문 유형 필드) 으로 나눠 받고 A안만 승인.
- **작업 단위 승인**: "전체 개발을 한 번에 승인하지 않고, 작업 단위로 검토하고 진행하겠습니다. … 완료 후에는 다음 작업을 자동으로 진행하지 말고 결과를 먼저 보고해 주세요." (P0-01 ~ P0-05, E-1 ~ E-5)
- **프롬프트 보호**: 11-02 내내 "`prompts.py` 수정 금지"를 반복 → "prompts.py 수정은 사용자 승인 필요" 로 정리. 그래서 프롬프트 변경은 두 번(4-3 · 4-4)뿐이고 모두 사용자 승인 문구가 있다.
- **지어내지 않기를 작업에도 적용**: "현재 코드에 없는 기능을 구현된 것처럼 설명하지 말고" · "수동 점검을 하지 않은 항목을 통과로 표시하지 마세요." · "오류를 예외 처리로 숨기지 마세요."
- **민감정보 규칙**: "사용자 답변 전문, 개인정보, API 키, 인증 토큰, AI 응답 전문은 기록하지 않습니다." (오류 기록 설계) · 실제 API 테스트는 호출 횟수를 정해 승인 ("실제 API 호출 3회 - SDK 자동 재시도 포함 최대 9건").
- **질문 은행 확장**: "질문 목록을 제가 승인하기 전에는 실제 질문 은행에 반영하지 마세요." → 90문항 초안을 먼저 받고 승인 후 반영. "실제 OpenAI API로 질문을 새로 생성하는 기능은 추가하지 않습니다." (질문 은행 방식 유지)

## 06. 현재 한계와 향후 개선

### 6-1. 현재 구현된 AI 기능
- 면접관 반응 · 꼬리 질문(질문당 최대 1개, 코드 강제) · 이해도
- 평가 위원 4명 채점 · 답변별 기준 4개 · 다듬은 답 · 확인할 사실 · 다음 연습에서 고칠 것 (응답 검증 · 자동 1회 재요청 · 범위 밖 점수 보정)
- 재도전 채점 (횟수 제한 없음 · 같은 질문의 최고 점수 반영)
- 형광펜 · 전략 가이드 (사용자가 요청할 때만 호출)

### 6-2. 코드에는 있지만 쓰지 않거나, 명세만 있는 것
| 항목 | 현재 상태 | 근거 |
|---|---|---|
| 마지막에 할 질문 다듬기 · 추천 (`LAST_QUESTION` · `LAST_SUGGEST`) | 프롬프트 · 함수는 있으나 MVP1 화면에서 뺌. 유지 여부 결정 필요 | `prd/MIGRATION.md` |
| 피드백형 면접관 (`INTERVIEWER_FEEDBACK`) | 프로덕트 디자인 리드를 필요 없다고 판단해 삭제(사용자 결정)해서 실행되지 않음 | `prd/MIGRATION.md` · 4-2 |
| 꼬리 질문 유형 정책 (실무 근거 검증 기본 · 경험 탐색 보조) | 한도(1개)만 구현, 유형 정책은 미구현. 유형을 별도 필드로 넘기는 B안은 보류 | `prd/MIGRATION.md` · 4-3 |

### 6-3. 향후 프롬프트 개선 방향 (문서 · 기록에 근거한 것만)
1. **Claude Code 초안 확정**: 개발 · PO · 마케팅 면접관 글, `FIELDS`, `HIGHLIGHT`, `STRATEGY` 는 "사용자 확인 필요" 상태다. 사용자가 문장을 확정해야 한다 (`CLAUDE.md` "프롬프트는 내가 쓴다").
2. **실제 응답 품질 점검**: `manual_checklist.md` §11 (A-1 ~ A-6) 을 실제 API 로 돌려 결과를 남긴다. 특히 꼬리 질문 개선(4-3)과 [보는 점] 반영(4-4)의 효과는 아직 정량 확인이 없다. 응답 원문은 저장하지 않는 규칙을 지키며 구조 · 점수 · 글자 수만 기록한다.
3. **꼬리 질문 유형 (B안)**: 질문 유형(직무 · 경험 · 상황)을 별도 필드로 넘겨 가정형 · 경험형 질문을 프롬프트가 더 분명히 구분하게 하는 방안 — 보류된 상태.
4. **평가 기준 버전 기록**: 프롬프트 · 기준이 바뀌어도 과거 평가와 비교할 수 있게 `rubric_version` 을 평가 결과에 남긴다 (AI_RULES 명세).
5. **검증 실패 모니터링**: "검증 실패가 반복되면 프롬프트와 평가 기준 자체를 점검한다" (PRD · AI_RULES). 점수 보정 발생률 기록은 후속 검토 항목이다.
